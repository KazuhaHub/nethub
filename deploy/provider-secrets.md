# Provider credential encryption

The Web process now loads the deployment's existing provider-encryption key and
holds a cipher on its console repository. The bounded, versioned envelope is
implemented and tested. Provider administration, actual credential database
writes, discovery and OIDC/SAML login are still W6 work; this foundation does not
establish that provider secrets are already stored or managed through the API.

## Key ownership and startup

`nethub init` already creates `secrets/web/secrets_key`: 32 random bytes encoded as
64 lowercase hexadecimal characters and a newline. It is the deployment key called
`NETHUB_SECRETS_KEY` in DESIGN. Supply it through the private file, not a plaintext
environment variable or command argument containing the key itself.

Generated commands in both proxy modes explicitly set
`--secrets-key-file /run/secrets/secrets_key`. This is also the CLI default so
existing generated bundles keep using their existing mounted key. Manual Web
invocations must make that private file available or pass its path explicitly.
The key is not regenerated by Web startup. Other services do not receive its mount.

Web refuses a missing, malformed, linked or group/world-readable key before
opening the database or listener. POSIX mode checks apply on Unix; Windows uses
its filesystem access controls. Diagnostics disclose neither key bytes nor the
private file path. Existing bounded private-file loading is reused. A reloaded
key opens existing envelopes; replacing or losing the key cannot do so. Preserve
it with the private deployment backup. Automatic key rotation and reencryption
are not implemented.

## Envelope contract

The cipher accepts exactly 32 key bytes and uses AES-256-GCM through the standard
library's [random-nonce API](https://pkg.go.dev/crypto/cipher#NewGCMWithRandomNonce).
The first byte is envelope version 1, followed by the library's 12-byte random
nonce, ciphertext and 16-byte authentication tag. No caller supplies the nonce.
The same key must encrypt fewer than 2^32 messages across all its uses.

Authenticated data includes a fixed versioned domain and separately
length-prefixed tenant ID, provider ID and purpose. Use identifiers read from the
authoritative storage row. OIDC client secrets and SAML signing keys have distinct
purposes. Moving ciphertext between tenants, providers or purposes fails even
when the deployment key is the same. Identifiers are opaque, nonempty values up
to 64 bytes; account/provider policy remains outside the cipher package.

Plaintext is bounded to 1–16384 bytes. Absence or explicit removal of an optional
credential must be represented by the future storage contract, not an encrypted
empty string. Unknown versions, truncated or oversized envelopes, tampering and
wrong context/key return one fixed error and no partial plaintext. Cipher debug
and JSON formatting do not expose its expanded key material.

## Validation boundary

Tests exercise randomized output, every-byte tampering, context and key
substitution, input bounds, concurrent use and safe diagnostics. CLI tests load
the same file twice, open an existing envelope, and refuse invalid material before
database startup. Generated-command tests cover both bundled and external proxy
modes. The isolated deployment suite must additionally start the actual Web image
with its generated key and verify missing, malformed and unsafe-key refusal in
separate containers with no network or database access. Hosted execution and
actual logs are required before accepting that deployment behavior.

Future provider tests must prove encryption before actual database writes,
write-only credential fields, atomic audits, live administrator checks and
discovery safety. This package is application storage policy; SAML protocol
orchestration continues to use authcore, and matching OIDC orchestration belongs
there as well.
